## Key Outcomes

### Delinquent Vendor Resolution
- **"Use Previous" and "Exclude" Buttons:** Resolution column added to the vendor table on `/review/`. Each unverified vendor row shows two action buttons — "↩ Use Previous" (carry forward last published records into staging as SUBMITTED) and "✕ Exclude" (remove staging rows and mark audit verified with no_change=True).
- **Resolution Modal:** `<div id="dq-modal-overlay">` modal with contextual title, description, error display, and confirm button. Opened via `openDelinquentModal(vendor, action)`; confirmed via `confirmDelinquent()` AJAX POST to `/review/handle-delinquent/`.
- **`reviewer_handle_delinquent` View:** New AJAX POST endpoint. For `use_previous`: queries most recent RentalMaster rows per equipment_id for the vendor, bulk-creates them into RentalStaging for the current week with `status=SUBMITTED` and a "Carried forward" note. For `delete`: clears all staging rows for the vendor. In both cases, VendorAudit is set to `verified=True`. URL: `/review/handle-delinquent/`.
- **Bug Fixed — `models.Q` NameError:** Initial implementation used `models.Q()` but `models` is not imported in views.py (only `Q` is). Fixed by replacing `models.Q(...)` with `Q(...)`.
- **Delinquent Banner:** Orange warning banner above the vendor table when any vendors are unresolved. Count updated dynamically as vendors are resolved.
- **Auto-Flow into Publish:** When the reviewer clicks Publish with delinquent vendors remaining, `openPublishModal()` now intercepts, sets `_publishAfterDQ = true`, and opens the delinquent modal for the first unresolved vendor. After each resolution, the next delinquent is prompted automatically until all are resolved, then the publish modal opens.

### Email-Based Two-Factor Authentication
- **LoginOTP Model (migration 0014):** Fields: `user` (FK to User), `code` (CharField max_length=6), `created_at`, `is_used` (BooleanField). `OTP_EXPIRY_MINUTES = 10`. `is_valid()` method checks expiry and `is_used`.
- **`portal_login` Rewritten:** On valid credentials, invalidates prior OTPs for the user, generates a 6-digit code via `secrets.randbelow(1_000_000)` (zero-padded), creates a `LoginOTP`, emails the code, stores `_2fa_pending_user_id` and `_2fa_next` in session, and redirects to `/login/verify/`.
- **`verify_otp` View:** Reads `_2fa_pending_user_id` from session, validates submitted code against the latest unused unexpired `LoginOTP`, calls `auth_login()` on success, and redirects to the appropriate home page by role.
- **`verify_otp.html` Template:** Full two-panel card layout matching `login.html`. Large monospace OTP input, auto-submit on 6-digit entry, "Back to login" link, 10-minute expiry note, error display.
- **Email Backend:** `console.EmailBackend` in dev (when `EMAIL_HOST=localhost`); SMTP backend otherwise. OTP prints to the Python terminal in dev. Real delivery requires Gmail app password via environment variables.
- **2FA Verification Status:** OTP flow working end-to-end in dev (code visible in terminal). Live Gmail SMTP delivery deferred to next session — Gmail app password not yet configured.

### Inline Category & Vendor Editing in Consolidated Table
- **TYPE OF EQUIP. Bug Fixed:** Template was rendering `vendor_code` in column 4 instead of `equipment_category`. Fixed by binding the cell to `row.equipment_category`.
- **Equipment Category Dropdown:** TYPE OF EQUIP. column in the consolidated reviewer table is now double-click editable. Opens a `<select>` populated from the same `ApprovedEquipmentCategory` list vendors use. `reviewer_inline_save` validates the submitted value against the approved list before saving.
- **Rental Co. Dropdown:** RENTAL CO. column also converted to a `<select>` dropdown populated from active `VendorCompany` names. `reviewer_inline_save` validates against active vendors.
- **JS `editCell()` Updated:** Now handles `type='select'` in addition to `type='text'` and `type='date'`. Option list is selected by field name: `vendor_name` → `REVIEW_VENDORS`, all others → `REVIEW_CATEGORIES`.

### Publish Gate Relaxed
- **Amber "Publish (N pending)" Button:** When not all vendors are verified, the Publish button no longer disappears — it becomes amber with a tooltip indicating how many responses are still pending. Reviewer can click it at any time.
- **Server-Side Hard Block Removed:** The `if not can_publish: return redirect(...)` guard in `publish_week` was removed. `can_publish` is still computed and used for button color/tooltip in the template, but publishing proceeds regardless.
- **Publish Only Includes Submitted Rows:** Pending/unverified vendors simply have no SUBMITTED staging rows, so they are naturally excluded from the publish batch. Correct behavior without blocking the workflow.

### Staging Integrity Enforcement
- **Validation Blocks Publish:** If `/review/validate/` returns any row-level errors, the Confirm & Publish button in the publish modal is grayed out (`disabled`, `cursor:not-allowed`, tooltip) until errors are fixed. Reviewer must correct the flagged rows before publishing can proceed.

## Decisions
- **OTP via `secrets` Module:** `secrets.randbelow(1_000_000)` chosen over `random` for cryptographic safety. Zero-padded to 6 digits.
- **Gmail SMTP Deferred:** Live email delivery deferred one session. Dev OTP printed to terminal is sufficient for current testing. App password will be configured next session.
- **Publish Gate Design:** Keeping `can_publish` computed (for UI color) but removing the redirect guard gives reviewers control while the system still signals state clearly.
- **Delinquent Auto-Prompt on Publish Click:** Rather than forcing reviewers to scroll the vendor table before publishing, the publish button now drives the resolution workflow automatically — ensuring no vendor is overlooked before the publish modal opens.
