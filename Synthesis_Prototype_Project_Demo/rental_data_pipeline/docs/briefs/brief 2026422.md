## Key Outcomes

### W17 Scenario Simulation (Core Work)
- **`simulate_vendor_week` Command Created:** New management command accepts `--week N` and orchestrates the full W17 scenario matrix. For each scenario, the command creates or updates `RentalStaging`, `VendorAudit`, and related records. `--dry-run` flag previews all planned actions without DB commits. Scenario assignments are deterministic by vendor index so results are reproducible.
- **S-01 — No Change (4 vendors):** `no_change=True` set on `VendorAudit`; `verified=True`; no staging rows created. All four appear with "No Changes" badge on `/review/`.
- **S-02 — New Equipment Added (2 vendors):** Two staging rows each created with new `equipment_id` values not present in W16 master. Both passed validation (`is_validated=True`). Published to master. Week Comparison tab confirmed both vendors' new equipment in "Placed On-Rent" column.
- **S-03 — Equipment End-Dated (2 vendors):** Staging rows submitted with `on_rent_end` set to the W17 cycle end date. After publish, Week Comparison tab confirmed affected equipment appeared in "Taken Off Rent" column. `on_rent_start <= on_rent_end` constraint validated cleanly.
- **S-04 — Rate Change (1 vendor):** Existing equipment line resubmitted with updated `rate_daily`. Staging row passed validation. After publish, Cost Over Time chart reflected increased spend for the affected vendor in the W17 period.
- **S-05 — Validation Failure (1 vendor):** Staging row submitted with a malformed date string (`"not-a-date"`) and `rate_daily = 0`. Both fields failed validation: `is_validated=False`, `validation_errors` field populated with `"on_rent_start: Enter a valid date. | rate_daily: Ensure this value is greater than 0."`. Row correctly excluded from publish batch. Error count shown on `/review/` validation summary widget.
- **S-06 — Late Submission (1 vendor):** `VendorAudit.submitted_at` set to Thursday 14:15 CST (past the 14:00 cutoff). `is_late=True` set on audit record. Running `check_deadlines --cycle-date 2026-04-23` correctly identified this vendor as late and triggered SMTP nudge to their `UserProfile.vendor_email`.
- **S-07 — Non-Submission (1 vendor):** No action taken for this vendor during the simulated week. Audit remained `verified=False`. Vendor appeared as "Pending" on `/review/` stat card and vendor table. Included in `check_deadlines` output as unverified past cutoff.
- **S-08 — Duplicate Equipment ID (1 vendor):** Vendor attempted to POST the same `(vendor_name, equipment_id)` pair twice for the same week. Second submission detected by duplicate query check in the vendor submission view; rejected with a `400 Bad Request` and a human-readable validation message. First row retained in staging unaffected.

### Email Infrastructure
- **`generate_vendor_emails` Command Created:** Assigns `vendor_{company_slug}@example.com` to each of the 25 vendor `UserProfile` records via the `vendor_email` field. Command is idempotent; skips vendors with an email already assigned unless `--reset` flag is passed. Output confirms count of addresses assigned.
- **SMTP Lookup from UserProfile:** Removed hardcoded recipient list from `check_deadlines`. Command now queries `UserProfile.objects.filter(external_user=True)` and resolves email from `vendor_email` field. Falls back to a console warning if a vendor account has no email assigned.
- **Submission Receipt Hook:** Django `post_save` signal (or view-layer call) dispatches a confirmation email to `vendor_email` after each successful "Submit" action from `/vendor/`. Email body includes vendor name, cycle week number, and either submitted row count or "No Changes declared" text. SMTP credentials sourced from environment variables exclusively.
- **`validate_staging_batch` Command Created:** Re-validates all `RentalStaging` rows for a given `--week`. Calls each row's `clean()` method and updates `is_validated` and `validation_errors` in place. Prints a per-row summary table to stdout. Supports `--dry-run` to report without writing. Used to verify S-05 recovery: after correcting the malformed row manually in admin, re-running the command updated `is_validated` to `True`.
- **`/review/` Validation Summary:** Added a small widget above the vendor table on `/review/` showing count of staging rows with `is_validated=False`. Clicking the count opens a pre-filtered Django admin view (`/admin/rentals/rentalstaging/?week=N&is_validated__exact=0`). Widget disappears when all rows pass validation.

## Decisions
- **Scenario Assignment:** Deterministic by vendor index rather than random to ensure reproducibility across test runs. `--reset` flag not provided — scenarios are stable identifiers for the capstone demonstration.
- **Email Domain:** `@example.com` used for all fake addresses. RFC 2606 reserved domain ensures no real email delivery occurs during testing.
- **Duplicate Detection Layer:** Duplicate check placed in the view (not model `clean()`) so the error response is user-facing and does not silently discard data. Model layer remains agnostic to week context.
- **SMTP Fallback:** If `vendor_email` is blank, `check_deadlines` logs a console warning rather than raising an exception. Prevents one missing address from blocking the full deadline run.
- **Approval Email Deferred:** Post-publish approval confirmation email pushed to Phase 2.4. Adding it now would require a broadcast loop over all verified vendors — acceptable post-capstone complexity.
