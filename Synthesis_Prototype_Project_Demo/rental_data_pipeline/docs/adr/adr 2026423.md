## Problem Statement
The reviewer workflow lacked a mechanism for resolving delinquent (non-responding) vendors before publishing, the portal had no second authentication factor, the consolidated staging table had field binding and editability defects, and the publish gate was an absolute blocker that prevented publishing even when only monthly/optional vendors were unverified.

## Business Goals
- Ensure reviewers can resolve delinquent vendors (carry forward prior data or exclude) without requiring admin intervention, so weekly publishing is never permanently blocked by a single non-responding vendor.
- Harden portal authentication by adding a time-limited email OTP as a second factor for all user types (admin, reviewer, vendor).
- Allow reviewers to correct category and vendor assignment errors directly in the consolidated table without leaving the review page.
- Give reviewers agency over publishing timing — the system warns of pending vendors but does not block the action.

## Architecture Decisions

### ADR-2026423-01: Email OTP as Second Authentication Factor

**Decision:** Implement a server-side OTP model (`LoginOTP`) rather than using a third-party library (e.g. `django-two-factor-auth`, `django-otp`). Codes generated via `secrets.randbelow(1_000_000)` (CSPRNG), zero-padded to 6 digits, with 10-minute expiry and single-use invalidation.

**Rationale:**
- Third-party 2FA libraries introduce TOTP app dependency (Google Authenticator, Authy) which is inappropriate for vendor users who may not have mobile access during portal use.
- Email OTP requires no client-side application and is familiar to non-technical users.
- A purpose-built model keeps the implementation transparent, auditable, and tightly scoped to the portal's session flow.
- `secrets` module is the Python standard library CSPRNG, suitable for security-sensitive token generation per OWASP guidance.

**Consequences:**
- OTP delivery depends on a working SMTP configuration. Dev environment uses `console.EmailBackend` (code printed to terminal). Production requires Gmail app password via environment variables.
- OTPs are invalidated on use and expire after 10 minutes. Prior OTPs for a user are invalidated on new login attempt, preventing replay across sessions.
- All portal users (admin, reviewer, vendor) pass through the 2FA step. No bypass path exists once credentials are validated.

**Status:** Implemented. Live Gmail SMTP delivery pending app password configuration (deferred to 2026-04-25).

### ADR-2026423-02: Delinquent Vendor Resolution at Publish Time

**Decision:** Add "↩ Use Previous" and "✕ Exclude" action buttons to the reviewer vendor table. When the reviewer clicks Publish with unresolved delinquents, the system auto-prompts for each one sequentially before opening the publish modal, rather than allowing the reviewer to publish over unresolved vendors silently.

**Rationale:**
- Requiring explicit resolution of each delinquent vendor ensures the reviewer makes a conscious data decision for every missing response — no vendor is implicitly excluded by inaction.
- Auto-prompting from the Publish button creates a guided workflow; the reviewer cannot accidentally skip the resolution step.
- Separating "use previous" from "exclude" gives reviewers a meaningful choice with data consequences (prior data carried forward vs. zero contribution).

**Consequences:**
- `reviewer_handle_delinquent` view performs a bulk RentalMaster query to copy the most recent prior published row per equipment_id for the vendor into RentalStaging.
- If the vendor has no prior published data, "use previous" results in zero staging rows added — the vendor is still marked resolved with no contribution.
- VendorAudit is set to `verified=True` in both cases, so `_publish_readiness_for_cycle` no longer counts them as blockers.

### ADR-2026423-03: Publish Gate Downgraded from Hard Block to Advisory

**Decision:** Remove the server-side `return redirect()` guard in `publish_week` that prevented publishing when any vendor was unverified. Replace the non-clickable "Awaiting N response" span with an amber button that opens the publish modal normally.

**Rationale:**
- Monthly vendors (cadence="monthly") are only required at month-end. Blocking weekly publishes because a monthly vendor hasn't responded is incorrect workflow behavior.
- The delinquent resolution mechanism (ADR-2026423-02) provides the reviewer with an explicit path to handle non-responders before publishing; a hard block is redundant and counterproductive.
- The system still communicates state clearly via button color (blue = all resolved, amber = N pending) and tooltip.

**Consequences:**
- Publishing with pending vendors only includes rows with `status=SUBMITTED`. Pending vendors have no submitted rows and are naturally excluded from the publish batch.
- `can_publish` and `publish_blocker_count` are still computed and passed to the template for UI rendering but no longer gate the view action.

### ADR-2026423-04: Reviewer Inline Editing Uses Dropdowns for Constrained Fields

**Decision:** RENTAL CO. and TYPE OF EQUIP. columns in the consolidated reviewer table use `<select>` dropdowns (populated from `VendorCompany` names and `ApprovedEquipmentCategory` respectively) rather than free-text inputs.

**Rationale:**
- Free-text entry for these fields would allow reviewers to introduce invalid values that fail staging validation and block publish.
- Constraining to the approved list at the UI layer eliminates the class of integrity errors seen in W17 (e.g. "Mobile Locker Room Trailer is not in the approved list").
- The same approved list already constrains vendor input — reviewer editing should be no less strict.

**Consequences:**
- `reviewer_inline_save` validates both `vendor_name` (must be an active VendorCompany) and `equipment_category` (must be in ApprovedEquipmentCategory) server-side, regardless of what the UI sends.
- `editCell()` JS function extended to handle `type='select'`; option list selected by field name at runtime.

## Data Model Changes
- **`LoginOTP` model added** (migration 0014): `user` FK, `code` CharField(6), `created_at` DateTimeField, `is_used` BooleanField. No schema changes to existing models.

## Security Notes
- OTP codes generated via `secrets.randbelow` (CSPRNG). No use of `random` module for security-sensitive values.
- Prior OTPs invalidated on each new login attempt to prevent stale code reuse.
- `_2fa_pending_user_id` stored in session (server-side); not exposed in URL or cookie.
- All SMTP credentials sourced from environment variables. No credentials in source.
