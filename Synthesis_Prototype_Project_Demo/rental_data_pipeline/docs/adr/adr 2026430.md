Session Date: 2026-04-30
Owner: Alexander J. Lawson
Status: Updated
Related Plan: ../Implementation Plan.md

## Problem Statement
The vendor submission workflow had no time boundary — vendors could theoretically submit or edit data after the reviewer had already published that week's ledger, introducing a race condition between submission and publication. There was also no practical mechanism for a developer to reset a published week during testing without manually deleting rows. Separately, the `VendorCompany` model had no `cadence` field, so `advance_cycle` hardcoded `"weekly"` for every audit record — rendering the `SubmissionCadence` enum on `VendorAudit` non-functional and treating all 6 monthly vendors as weekly reporters.

## Business Goals
- Guarantee that vendors cannot submit changes after the reviewer has published that week's data.
- Give developers a repeatable way to reset a published week and bulk-pre-fill vendor submissions during manual testing.
- Restore per-vendor cadence tracking so the weekly review table can correctly distinguish weekly from monthly reporters and compliance analytics are accurate.

## Architecture Decisions

### ADR-2026430-01: Publication State as Implicit Submission Window Gate

**Decision:** The vendor submission window is determined at request time by checking whether `RentalMaster` rows exist for the current ISO `cycle_week` and `cycle_year`. No dedicated "window open/closed" flag or timestamp is stored. The window is open while no master rows exist for the week; it closes the instant the reviewer publishes.

**Rationale:**
- `RentalMaster` publication is already the authoritative, durable event that marks a week as complete. Using it as the gate avoids introducing a second source of truth (e.g. a boolean flag on `VendorAudit` or a new model) that could drift out of sync.
- The check is a single indexed `EXISTS` query (`filter(cycle_week=w, cycle_year=y).exists()`). It adds negligible overhead to the four affected view calls.
- `reset_week` (ADR-2026430-02) fully reverses publication by deleting master rows, which also reopens the window automatically with no additional state management.
- Consistent with the existing `vendor_dashboard` pattern where publication state is already derived from queryset presence, not stored flags.

**Consequences:**
- If an admin seeds or otherwise inserts master rows for a future week, the window for that week will appear closed to vendors. This is acceptable and intentional for a controlled internal tool.
- The check is stateless and idempotent — re-publishing after a reset is handled exactly like a first publish with no special-case logic.

**Status:** Implemented.

### ADR-2026430-02: `reset_week` and `bulk_submit_vendors` as Test-Only Management Commands

**Decision:** Two management commands are added exclusively for developer/test use. `reset_week` deletes all `RentalMaster` rows for a target week and resets `VendorAudit` records to their initial pending state. `bulk_submit_vendors` marks all vendor audit records as submitted for a target week, leaving one configurable vendor pending for manual walkthrough.

**Rationale:**
- The full submission → review → publish cycle involves 25 vendors and requires both a vendor login and a reviewer login. Without test utilities, re-testing the cycle from scratch would require 25 manual submissions or direct DB manipulation.
- Management commands are the idiomatic Django approach for privileged, scriptable operations that don't belong in a web endpoint. They run only from a trusted terminal with filesystem access to the project, not from any web-exposed surface.
- Keeping the commands in `management/commands/` rather than a separate test runner means they are co-located with the other operational commands (`advance_cycle`, `seed_ledger`, `check_deadlines`) and can reuse the same Django ORM context.
- The `--skip` argument on `bulk_submit_vendors` and `--week`/`--year` on both commands make them flexible for testing different scenarios without code changes.

**Consequences:**
- `reset_week` is destructive: it deletes published master rows. README documents this explicitly. No web-accessible endpoint exposes this operation.
- `bulk_submit_vendors` stamps staging rows with `cycle_week/cycle_year` to mirror what a real vendor CSV upload would produce, ensuring the review page behaves consistently during testing.

**Status:** Implemented.

### ADR-2026430-03: Cadence Stored on VendorCompany, Propagated to VendorAudit at Cycle Creation

**Decision:** Add a `cadence` CharField (`weekly`/`monthly`, default `weekly`) to `VendorCompany`. `advance_cycle` reads cadence from `VendorCompany` and stamps each newly created `VendorAudit` record with the appropriate value. The cadence on an audit record is set once at creation and treated as a snapshot — changes to `VendorCompany.cadence` propagate only to future cycles.

**Rationale:**
- `VendorAudit` already had the `cadence` field and the `SubmissionCadence` enum but had no authoritative source to populate it from. Storing cadence on `VendorCompany` makes it the single source of truth, editable via Django admin without requiring a code change.
- Snapshotting the cadence onto each `VendorAudit` row (rather than always looking it up from `VendorCompany` at read time) preserves historical accuracy — if a vendor switches from monthly to weekly mid-year, prior audit records correctly reflect their cadence at that time.
- A single `values('name', 'cadence')` query in `advance_cycle` fetches all company cadences in one DB round-trip before the creation loop.
- All 69 existing audit records were backfilled with the correct cadence in a one-time migration script.

**Consequences:**
- Future `advance_cycle` runs will correctly stamp new audit records with the cadence from `VendorCompany`. No further manual backfills are needed unless data is reseeded from scratch.
- Django admin can update `VendorCompany.cadence` for any vendor; the change takes effect on the next `advance_cycle` run.
- The weekly review page and compliance analytics can filter or group by `VendorAudit.cadence` to distinguish monthly reporters from weekly ones.

**Status:** Implemented.
