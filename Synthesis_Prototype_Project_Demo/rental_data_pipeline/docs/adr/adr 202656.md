## Problem Statement
With the capstone submission window open, the project required a final pre-submission audit. Several issues were identified: (1) the `demo_setup` management command printed a hardcoded `vendor_smith_llc` in its vendor flow walkthrough header regardless of the `--skip` argument passed at runtime, making the output misleading when any other vendor was designated pending; (2) the Quick Start command in the prototype README used `--skip vendor_brown_group`, which caused Smith LLC — the vendor with no real W19 data — to be auto-submitted and show as Verified on the vendor portal; (3) grader-facing commands in the README used `--reset` for session resets, which preserved staging rows and could leave a dirty state, while `--full-reset` was the correct flag for a guaranteed clean slate; (4) the synthesis paper and prototype README still carried an April 2026 date; (5) training certificate references (Pluralsight, DataCamp) remained in the BA and SS pillar assignments and the BA README, creating unverifiable external claims.

## Business Goals
- Ensure every command in the grader-facing README is correct, consistent, and produces the documented state when run.
- Remove all references to unverifiable training platform certificates so the portfolio presents only artifacts that exist.
- Correct all date fields to May 2026 for submission accuracy.
- Leave the application and repository in a state that can be cloned, set up, and graded without any manual correction.

## Architecture Decisions

### ADR-202656-01: `demo_setup` Walkthrough Header Uses Dynamic Skip Username

**Decision:** The terminal walkthrough printed by `demo_setup` at the end of every run now derives the vendor flow header label from the `skip_username` variable resolved at runtime rather than the hardcoded string `"vendor_smith_llc"`.

**Rationale:**
- The walkthrough is the primary operator guidance output. If a grader runs `demo_setup --skip vendor_brown_group`, the printed instructions must match the actual state — printing `vendor_smith_llc` when Brown Group is pending is a direct contradiction that could cause a grader to log in as the wrong vendor.
- The fix is a one-character change: replace a string literal with the already-resolved variable. No architectural impact.
- The default (`vendor_smith_llc`) is unchanged; the fix only affects runs that explicitly pass `--skip`.

**Status:** Implemented.

---

### ADR-202656-02: Quick Start Defaults to `vendor_smith_llc` as the Pending Demo Vendor

**Decision:** The Quick Start command and all grader-facing walkthrough steps use the bare `demo_setup --full-reset --backfill` (no `--skip` flag), relying on the `DEFAULT_SKIP = "vendor_smith_llc"` code default. The README no longer includes `--skip vendor_brown_group` in any grader-facing command.

**Rationale:**
- Smith LLC is the vendor that did not submit real W19 data. Using any other vendor as the pending demo vendor creates a logical inconsistency: Brown Group (or any other vendor) submitted real data and would show as Verified on login, breaking the vendor portal demonstration.
- The `--skip vendor_brown_group` example remains documented in the command reference table as an advanced option, but it is removed from the Quick Start command, the Grading Flow steps, and the Full-Cycle Reset section.
- Maintaining `DEFAULT_SKIP = "vendor_smith_llc"` in the command source means the bare `demo_setup` command always produces the correct grading state with no flag required.

**Status:** Implemented.

---

### ADR-202656-03: All Grader-Facing Reset Commands Use `--full-reset`

**Decision:** Every grader-facing reset command in the README uses `--full-reset` rather than `--reset`. The `--reset` flag (soft reset, staging preserved) is retained in the command reference table as a developer option but is removed from Step 1, Step 6, Step 12, the Reviewer Flow table, and the Full-Cycle Reset section.

**Rationale:**
- `--reset` wipes master rows and resets audit records but leaves staging rows intact. If a grader has run any vendor submission during a prior test, leftover staging rows can cause unexpected state (e.g., the vendor portal showing pre-filled rows from a previous session).
- `--full-reset` wipes staging, master, and audit rows before opening the cycle, guaranteeing a clean slate regardless of what occurred in prior runs. This is the correct semantic for "start over."
- Graders are not expected to understand the difference between the two flags. Presenting a single unambiguous reset command removes a potential source of confusion.

**Status:** Implemented.

---

### ADR-202656-04: Training Certificate References Removed from Portfolio

**Decision:** All references to Pluralsight and DataCamp training platform completions are removed from the BA pillar assignment, BA README, and SS pillar assignment. Course names and skill areas are retained where they are referenced as WTAMU academic coursework by course number (e.g., CIDM 6303, CIDM 6312), not as platform certificates.

**Rationale:**
- Certificate screenshots from Pluralsight and DataCamp were not included in the submission package. Referencing them creates unverifiable external claims.
- The professional and applied artifacts (Power BI dashboards, Tableau work, Django application, SQL labs, k-means clustering) are the substantive evidence of competency. The platform certificate references added no verifiable value.
- Removing them simplifies the Consulted Sources sections to only citable, live-linked resources: official Microsoft Power BI documentation, Tableau Training Gallery, Django Project Documentation, Microsoft .NET C# Guide, and R Documentation.

**Status:** Implemented.
