# ADR - Architecture Decision Record

Session Date: 2026-04-24
Owner: Alexander J. Lawson
Status: Updated
Related Plan: ../Implementation Plan.md
Prior Session: adr 2026423.md

## Problem Statement
The analytics dashboard had two compounding performance defects: the server rendered the full ledger table as Django template HTML *and* transmitted the same data as an inline JSON blob, doubling page payload. The client-side filter walked every `<tr>` node in the DOM on each keystroke. Both defects made the page slow to load and unresponsive during filtering. Separately, a JavaScript `const` temporal dead zone error in the analytics script silently aborted the entire script block on page load, preventing both the ledger from rendering and the dark mode toggle from responding to clicks.

## Business Goals
- Eliminate analytics page load lag caused by server-side HTML row generation and redundant data transmission.
- Make ledger column filtering near-instant regardless of record count.
- Restore dark mode toggle to full functionality on all portal pages.
- Document all installed packages and environment requirements in the README for reproducibility.

## Architecture Decisions

### ADR-2026424-01: Client-Side Ledger Rendering via JS Data Array

**Decision:** Remove the Django template `{% for row in master_all %}` loop that generated `<tr>` rows server-side. Remove the `master_all` queryset from `analytics_dashboard` entirely. The ledger table body (`#ledger-tbody`) is populated exclusively by a JavaScript `buildLedgerRows(rows)` function that consumes the already-present `dashboardRows` JSON array and sets `innerHTML` with a concatenated string of `<tr>` markup.

**Rationale:**
- The prior implementation transmitted ledger data twice: once as rendered HTML rows (server-side Django template loop) and once as `dashboard_rows_json` for the chart logic. This doubled page weight for no benefit.
- String concatenation into `innerHTML` is significantly faster than creating individual DOM nodes for large datasets (1,695–6,587 rows).
- The existing `dashboardRows` JSON array already contained all chart-required fields; adding `on_rent_start`, `on_rent_end`, `sn_request_number`, and `approved_by__username` to the `dashboard_values` queryset made it complete for the ledger as well.
- `record_count` changed from `master_qs.count()` (a second DB query) to `len(dashboard_rows)` (free after list construction).

**Consequences:**
- Page HTML payload reduced by the size of ~6,587 `<tr>` elements (previously rendered twice).
- `downloadLedgerCsv()` continues to work — it reads cell text from the live DOM, which JS-rendered rows satisfy equally.
- The ledger has no progressive enhancement fallback if JS is disabled; this is acceptable for an internal reviewer-only analytics tool.

**Status:** Implemented.

### ADR-2026424-02: Data-Array Filter Replacing DOM Show/Hide

**Decision:** Replace `applyLedgerFilters()` — which iterated every `<tr>` in the DOM and toggled `style.display` on each one — with a function that filters the `dashboardRows` JavaScript array and replaces the entire `tbody.innerHTML` with only the matching rows.

**Rationale:**
- Toggling `display` on thousands of DOM nodes on each `input` event causes layout thrashing. The browser must recalculate layout for every change.
- Filtering a plain JS array and writing a single `innerHTML` assignment is O(n) with minimal DOM interaction, remaining fast even at 6,587 rows.
- The `week-picker` filter and the thirteen per-column text filters are all handled in a single pass over the data array.

**Consequences:**
- Column filter values are matched against a string-mapped representation of each record's fields, including `rate_daily.toFixed(2)` for the rate column.
- The counter (`#ledger-count`) reflects the number of matched rows in the filtered array, not DOM node visibility.
- `downloadLedgerCsv()` skips rows with `style.display === 'none'`; since the new implementation removes non-matching rows from the DOM entirely, this check is always false — all visible rows are exported correctly.

**Status:** Implemented.

### ADR-2026424-03: Dark Mode Wired in Isolated Early Script Tag

**Decision:** Move the dark mode initialization and button event listener out of the bottom-of-script IIFE and into a standalone `<script>` tag placed immediately after `<body>` in both `analytics.html` and `weekly_review.html`. The handler uses event delegation (`document.addEventListener('click', ...)`) rather than a direct `#theme-toggle` reference.

**Rationale:**
- The prior implementation placed the dark mode IIFE at the bottom of a large script block. A `ReferenceError` earlier in that block (caused by a `const TD` temporal dead zone — `const` declared after its first call site within the same script) silently aborted execution before the IIFE ran, leaving the toggle unresponsive.
- A dedicated `<script>` tag runs synchronously and independently; a crash in any other script block cannot prevent it from executing.
- Event delegation on `document` means the listener is active before the button element is parsed, eliminating any dependency on DOM readiness.
- Using `var` (not `const`) for the `TD` style string inside `buildLedgerRows()` eliminates the temporal dead zone that caused the original crash.

**Consequences:**
- Dark mode toggle is now resilient to any downstream JavaScript error on both portal pages.
- `localStorage` key `rdp-theme` persists the preference across sessions and page navigation, consistent with prior behavior.
- Both `analytics.html` and `weekly_review.html` share the same early-script pattern for consistency.

**Status:** Implemented.

### ADR-2026424-04: requirements.txt as Canonical Dependency Manifest

**Decision:** Generate `requirements.txt` from the active venv via `pip freeze` and commit it to the repository root. README updated to reference `pip install -r requirements.txt` as the primary install path.

**Rationale:**
- Prior README listed only `Django==6.0.4` and `plotly` — omitting `python-dotenv`, `apscheduler`, `pytz`, and all transitive dependencies. A fresh environment built from those instructions would fail at startup.
- `requirements.txt` from `pip freeze` is deterministic and version-pinned, ensuring reproducibility across machines and graders.
- A full dependency table in the README documents purpose for each package, satisfying project documentation requirements.

**Consequences:**
- All eleven packages (including transitive dependencies) are pinned to exact versions in `requirements.txt`.
- `.env` is documented in README with all required keys and is confirmed present in `.gitignore` — credentials are never committed.

**Status:** Implemented.

## Session 2 — UX Checklist Verification & Gap Analysis (2026-04-24, Evening)

### ADR-2026424-05: Static Code Verification as Primary Checklist Evidence Method

**Decision:** Rather than requiring a full manual browser walkthrough for every checklist item, use static code analysis (reading `views.py`, `middleware.py`, `settings.py`, `admin.py`, `management/commands/`, and all portal templates) as the primary evidentiary standard for confirming implementation of server-enforced behaviors. Items requiring UI/JS interaction remain ⬜ and are flagged for the owner's manual walkthrough.

**Rationale:**
- Server-enforced behaviors — role guards, redirect logic, CSRF middleware, sign-out form patterns, management command existence, admin registrations — are fully deterministic from source code. No runtime verification adds evidence value.
- Separating code-verifiable items from UI-verifiable items allows a single code-read pass to close the majority of the checklist without a live server dependency.
- Items that depend on JavaScript rendering, responsive layout, badge display logic, or chart interactivity genuinely require a browser and cannot be confirmed from source alone.

**Consequences:**
- 38 of ~62 pending checklist items verified ✅ from source.
- 4 OTP items (A-12 through A-15) marked N/A — 2FA disabled.
- 2 DV test items (DV-08, DV-09) marked N/A — `validate_staging_batch` command never implemented.
- Remaining ~20 items remain ⬜ for owner's manual browser walkthrough.
- One gap discovered: DV-06 — no duplicate `(vendor_name, equipment_id)` enforcement in `vendor_add_row` or `RentalStaging` model constraints.

**Status:** Analysis complete. Implementation Plan updated.

### ADR-2026424-06: DV-06 Duplicate Row Gap — Accepted as Known Limitation

**Decision:** The gap in DV-06 (no server-side duplicate check for identical `(vendor_name, equipment_id)` submissions within the same cycle) is documented as a known limitation and accepted for this capstone submission rather than fixed.

**Rationale:**
- Implementing the constraint correctly requires a decision on what uniqueness scope is appropriate: per-cycle (week + year), per-vendor only, or global. Each variant has different implications for multi-week roll-forwards and the "Use Previous" workflow.
- The vendor portal's inline edit workflow means a vendor typically updates existing rows rather than adding duplicates; the gap is only exploitable through the "Add Row" modal.
- Adding a unique constraint to `RentalStaging` at this stage would require a new migration and regression testing of the "Use Previous" carry-forward path.
- The risk in a capstone demo environment — where all vendor data is seeded by management commands — is negligible.

**Consequences:**
- DV-06 remains ⬜ in the Implementation Plan with a gap note.
- A future implementor would add `UniqueConstraint(fields=["vendor_name", "equipment_id", "cycle_year", "cycle_week"], ...)` to `RentalStaging.Meta` and handle `IntegrityError` in `vendor_add_row`.

**Status:** Accepted limitation. No code change.
