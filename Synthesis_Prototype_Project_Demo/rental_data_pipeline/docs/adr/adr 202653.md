# ADR - Architecture Decision Record

Session Date: 2026-05-03
Owner: Alexander J. Lawson
Status: Updated
Related Plan: ../Implementation Plan.md
Prior Session: adr 2026430.md

## Problem Statement
Several UX and data integrity gaps surfaced after the W19 demo setup. All 25 vendors were seeded with `"weekly"` cadence regardless of their actual reporting frequency; `VendorAudit.cadence` (a snapshot field) was never corrected when `VendorCompany.cadence` changed. `demo_setup` skipped `advance_cycle` after a `--reset`, leaving some vendor rows missing from the cycle. The welcome modal on the vendor dashboard had no dismiss path, trapping vendors on the confirmation screen. The reviewer's `/review/` landing defaulted to the current ISO week even when that week was already published or had no open audits. The vendor portal had no way to communicate to a vendor that their next window had not opened yet. Monthly vendors had no documented or system-enforced rule for which specific week their submission was due.

## Business Goals
- Ensure `VendorAudit.cadence` always reflects the actual cadence of the vendor at the time of cycle creation, including for historical rows created before the fix.
- Give graders and reviewers a deterministic "first open week" on login rather than requiring manual navigation.
- Allow vendors to close the check-in modal without being forced to answer, and know when their next submission window opens.
- Surface whether monthly vendors are required to submit in the current review week, directly on the reviewer's pending-vendor banner.
- Eliminate the two missing vendor rows (Brown Group, Trevino Inc) that resulted from a partial `advance_cycle` run.

## Architecture Decisions

---

### ADR-202653-01: `_fix_vendor_cadences` Bulk-Updates Both `VendorCompany` and `VendorAudit`

**Decision:** `demo_setup`'s `_fix_vendor_cadences()` method now issues two ORM `bulk_update` calls — one to correct `VendorCompany.cadence` for all 25 companies, and a second to bulk-update `VendorAudit.cadence` across every historical audit row keyed by vendor name.

**Rationale:**
- `VendorAudit.cadence` is a snapshot field set at row-creation time. If the source (`VendorCompany`) was wrong when rows were created (all 25 seeded as `"weekly"`), every audit row produced before the fix is incorrect. Fixing only `VendorCompany` leaves the historical data wrong.
- Doing both corrections in a single `demo_setup` step 0a means the fix is idempotent and always applied before any backfill or reset — the rest of the command operates on clean data.
- Two bulk queries (one per cadence value) are more efficient than per-row saves and keep the correction atomic with respect to the rest of `demo_setup`.

**Consequences:**
- All historical `VendorAudit` rows are corrected on every `demo_setup` run, making re-seeding safe without manual DB intervention.
- The "NOT REQUIRED" KPI on `/review/` — which filters `audit.cadence == "monthly"` — now shows the correct count.

**Status:** Implemented.

---

### ADR-202653-02: `demo_setup` Always Runs `advance_cycle` After `--reset`

**Decision:** The `advance_cycle` sub-call in `demo_setup` now runs unconditionally when `--reset` is supplied, not only when zero audit rows exist. `advance_cycle` uses `get_or_create`, so existing rows are skipped and only genuinely missing vendor rows are created.

**Rationale:**
- `reset_week` resets rows in place rather than deleting them. If some vendor rows were never created in a prior partial run (e.g., Brown Group and Trevino Inc were absent from a premature W19 advance), `--reset` alone would leave them missing because "23 rows exist → skip `advance_cycle`" was the old gate.
- `get_or_create` makes re-running `advance_cycle` idempotent — no duplicates are produced, and the output clearly labels each row as created or skipped.
- The change ensures the post-reset state is always a fully populated cycle (25 vendors for the first week of the month, 19 for subsequent weeks).

**Consequences:**
- `advance_cycle` runs one extra time after `--reset`, adding negligible overhead (25 `get_or_create` calls).
- Post-reset cycle is always complete regardless of whether prior runs were interrupted.

**Status:** Implemented.

### ADR-202653-03: `reset_week` Corrects `VendorAudit.cadence` from `VendorCompany` After Bulk Reset

**Decision:** After `reset_week` bulk-resets audit rows to pending, it builds a `{name: cadence}` map from `VendorCompany` and individually corrects each audit row's `cadence` field before saving.

**Rationale:**
- The bulk `.update()` call resets status fields but does not touch `cadence`. If rows were created with the wrong cadence (all `"weekly"`), the reset would preserve the error.
- Correcting from `VendorCompany` at reset time ensures that even rows created before the cadence fix are repaired whenever a reviewer or developer resets a week.
- The correction loop iterates at most 25 rows — performance is not a concern.

**Consequences:**
- `reset_week` now depends on `VendorCompany` existing and having correct cadence data. This is a safe assumption given `seed_user_schema` sets cadence correctly.

**Status:** Implemented.

### ADR-202653-04: Reviewer Dashboard Auto-Advances to Nearest Open Cycle on Default Load

**Decision:** When `/review/` is loaded without explicit `?week=` / `?year=` query params, the view checks the current ISO week first; if it is already published or has no audit rows, it looks ahead up to four weeks to find the nearest unpublished week that has open audit records and sets that as the displayed week.

**Rationale:**
- The ISO week boundary is Monday. On Sundays the current ISO week (e.g. W18) is still "today" but the next cycle (W19) is the actionable one. Defaulting to W18 on Sunday forces reviewers to manually navigate forward every time.
- The lookahead stops at the first match, so if W18 is open and unpublished it is still shown — no week is skipped unless it is genuinely finished.
- Explicit `?week=` navigation is preserved so the `←` / `→` buttons and URL overrides continue to work exactly as before.

**Consequences:**
- Reviewers land on the most actionable week without manual navigation on any day of the week.
- If all upcoming weeks are unpublished but empty (no audits), the view falls back to the current ISO week (the four-week limit is exceeded and the default `current_week` stands).

**Status:** Implemented.

### ADR-202653-05: Vendor Dashboard "Done for Now" Banner with Next Window Date

**Decision:** The `vendor_dashboard` view computes a `done_for_now` boolean (true when the current week's audit is either absent or verified-and-window-closed, and a future audit row exists). When true, the template renders an orange banner stating the next submission window opens on a specific date and time (12:00 AM CST).

**Rationale:**
- Prior to this change, vendors who completed W18 or who logged in on a Sunday before W19 opened saw only a "Submission Window Closed" badge with no forward-looking information.
- The banner is derived from an existing `VendorAudit` query (the nearest future row) — no new DB queries are added beyond what `next_audit` already fetches.
- Displaying the exact date and time (in CST, the system's operational timezone) removes ambiguity for vendors in different time zones.

**Consequences:**
- The banner is only shown when a future audit row exists for the vendor. If no future cycle has been opened, no banner appears (graceful fallback).
- On Monday when W19 becomes the current ISO week, `done_for_now` evaluates to `False` and the banner disappears automatically.

**Status:** Implemented.

### ADR-202653-06: `welcomeModal` Dismissable via X Button and Backdrop Click

**Decision:** The vendor check-in modal (`#welcomeModal`) now has a close (×) button in the top-right corner and closes when the user clicks the dark backdrop outside the modal. Both actions set the session storage key so the modal does not reappear during the same browser session.

**Rationale:**
- The original modal had no escape path. Vendors who did not want to answer immediately were trapped on the page with no access to the header, navigation, or logout button.
- Setting the session key on dismiss (same as the "Yes" path) means the modal behaves consistently — once dismissed, it does not interrupt subsequent page loads in the same session.
- A shared `_closeWelcomeModal()` helper ensures the fade-out animation is applied identically across all three exit paths (Yes, No-confirmed, Dismiss).

**Consequences:**
- Vendors can bypass the check-in question without submitting, which is intentional — the question is informational guidance, not a gate. Submission still requires an explicit button click.

**Status:** Implemented.

### ADR-202653-07: `monthly_required` Flag Passed to Weekly Review Template

**Decision:** The `weekly_review` view computes `monthly_required` — a boolean that is `True` when at least one `VendorAudit` row for the current cycle has `cadence == "monthly"`. This is displayed in the existing yellow delinquent-vendor banner.

**Rationale:**
- The reviewer had no immediate signal indicating whether the 6 monthly vendors were expected to submit this week or had already fulfilled their monthly obligation in an earlier cycle. This was the primary source of confusion around the "NOT REQUIRED" KPI.
- Deriving the flag from the audit rows (rather than hardcoding the first-week logic) means it reflects the actual DB state — if a monthly vendor row was manually excluded or removed, the flag adjusts automatically.
- The banner already exists; augmenting its text rather than adding a new UI element keeps the interface clean.

**Consequences:**
- The flag adds a single aggregated boolean check to the `weekly_review` query cycle — negligible overhead.
- When all monthly vendors have already submitted via the `no_change` path in a prior week of the same month, their audit rows do not appear in the current cycle, so `monthly_required` correctly evaluates to `False`.

**Status:** Implemented.
