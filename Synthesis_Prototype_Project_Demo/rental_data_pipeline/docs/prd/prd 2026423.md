## Product Vision
A fully operational equipment rental data platform with a closed vendor compliance loop, email-based two-factor authentication for all portal users, a reviewer-driven delinquent vendor resolution workflow, and an inline-editable consolidated staging table with constrained dropdowns for all categorized fields. The platform enforces data integrity at every layer — vendor submission, reviewer correction, staging validation, and publish gating.

## Objectives
- Implement email OTP two-factor authentication for all portal user types (admin, reviewer, vendor).
- Give reviewers an explicit resolution workflow for delinquent (non-responding) vendors before publishing.
- Allow publishing with pending vendor responses — the system advises rather than blocks.
- Constrain reviewer inline editing of RENTAL CO. and TYPE OF EQUIP. to approved dropdown lists.
- Enforce staging integrity at publish time — gray out confirm button when validation errors exist.
- Correct all W17 staging rows with invalid equipment categories.

## Personas and Permissions
- Administrator: access-control and configuration management in Django admin.
- Junior Super User: weekly review, delinquent resolution, publish decisions, and analytics consumption via `/review/` and `/analytics/`.
- Vendor: submit equipment updates or declare no changes for the current cycle; restricted to own company data.

## Functional Requirements

### Two-Factor Authentication
- **FR-2FA-01:** After valid credentials, all portal users must be redirected to `/login/verify/` before any authenticated page is accessible.
- **FR-2FA-02:** A 6-digit OTP must be generated using `secrets.randbelow` (CSPRNG) and delivered to the user's registered email address.
- **FR-2FA-03:** OTPs expire 10 minutes after generation. Expired codes must be rejected with an error message.
- **FR-2FA-04:** OTPs are single-use. Once consumed, `is_used=True` is set and the code cannot be replayed.
- **FR-2FA-05:** Prior OTPs for a user are invalidated on each new login attempt.
- **FR-2FA-06:** `_2fa_pending_user_id` stored server-side in session only; not exposed in URL or response body.

### Delinquent Vendor Resolution
- **FR-DQ-01:** Every unverified vendor row must display "↩ Use Previous" and "✕ Exclude" buttons in the Resolution column.
- **FR-DQ-02:** "Use Previous" must copy the most recent published RentalMaster row per equipment_id for the vendor into RentalStaging for the current week, with `status=SUBMITTED`.
- **FR-DQ-03:** "Exclude" must delete all staging rows for the vendor for the current week.
- **FR-DQ-04:** Both actions must set `VendorAudit.verified=True` so the vendor no longer counts as a publish blocker.
- **FR-DQ-05:** Clicking Publish when delinquents remain must prompt resolution for each vendor sequentially before the publish modal opens.

### Reviewer Inline Editing
- **FR-EDIT-01:** RENTAL CO. and TYPE OF EQUIP. cells must open a `<select>` dropdown (not a text input) on double-click.
- **FR-EDIT-02:** `reviewer_inline_save` must reject any `vendor_name` not in the active VendorCompany list.
- **FR-EDIT-03:** `reviewer_inline_save` must reject any `equipment_category` not in the ApprovedEquipmentCategory list.
- **FR-EDIT-04:** On save, updated `equipment_category` and `vendor_name` must be returned in the JSON response and reflected in the table cell immediately.

### Publish Integrity
- **FR-PUB-01:** If `/review/validate/` returns row-level errors, the Confirm & Publish button must be `disabled` with `cursor:not-allowed` styling.
- **FR-PUB-02:** The publish view must not redirect based on vendor verification status; it must publish all SUBMITTED staging rows.
- **FR-PUB-03:** The publish button must be amber with a pending-count tooltip when vendors are unverified; blue when all are resolved.
